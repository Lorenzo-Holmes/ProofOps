# ProofOps 前端设计说明

## 1. 设计目标

ProofOps 的前端不是单纯的监控大屏，而是“产品叙事官网 + 可操作事故现场”的组合。产品区解释为什么可信 Agent Infra 需要证据、审批与验证；现场区让评委直接运行成功恢复、验证失败回滚和人工驳回三条路径。

参考来源仅用于通用设计原则：

- [Apple](https://www.apple.com/)：大标题、留白、单页叙事节奏与克制动效。
- [Vercel](https://vercel.com/)：近黑技术感、精确边框与工程可信度。
- [Linear](https://linear.app/)：分层暗色表面、状态表达与微弱光晕。
- [OpenAI](https://openai.com/)：编辑式排版、简洁导航与内容优先级。

页面不复制这些品牌的图标、插画、字体或具体布局。所有视觉均由 HTML 与 CSS 本地绘制。

## 2. 信息架构

1. **顶部导航**：品牌、产品/闭环/现场/开源锚点、后端连接状态。
2. **产品首屏**：一句价值主张、边界说明、现场入口与 CSS 闭环轨道。
3. **实时指标带**：事件、活动、恢复、回滚、审计完整度、Trace 覆盖。
4. **可信闭环原则**：证据先行、人工门禁、独立验证。
5. **协作契约**：6 Agent、8 Skill、1 审计链以及 Observe → Reason → Approve → Act → Verify 路径。
6. **现场工作台**：故障样本、事件队列、Agent 团队、状态机、时间线、证据、Skill 契约与审计链。
7. **审批对话框**：写操作前强制人工决策，批准与驳回均进入事件链。
8. **开源页脚**：仓库入口和项目定位。

## 3. 视觉系统

### 色彩

- 背景：`#070706`，避免纯黑导致层级消失。
- 主文字：暖白；次级文字：中性灰。
- 品牌信号：`#ff6a3d`，只用于入口、焦点和当前状态。
- 成功：绿色；警告：琥珀；错误/回滚：红色；信息：青色。
- 状态不能只依赖颜色，同时使用中文标签、边框与图形。

### 字体与尺度

- 使用 `system-ui`、`-apple-system`、`BlinkMacSystemFont`、`Segoe UI`，不加载外部字体。
- 首屏标题使用流体字号，桌面保持两行；移动端缩小并自然换行。
- Trace、哈希、Agent/Skill ID 使用系统等宽字体。
- 工作台保持紧凑，但交互控件最小点击尺寸为 44px。

### 表面与层次

- 产品区主要依靠留白、字号和 1px 边框形成层次。
- 卡片圆角 14–20px；工作台作为一个完整“设备表面”，避免每个字段都成为独立浮卡。
- 模糊仅用于顶部导航和审批遮罩；背景光晕静态呈现，不进行滤镜动画。

## 4. 交互与动效

- 导航和 CTA 使用页内锚点；目标设置滚动偏移，避免被固定导航遮挡。
- 闭环轨道仅旋转虚线，动画只改变 `transform`。
- 卡片悬停只使用轻微位移、边框和背景变化。
- 状态机使用 `data-current`、`data-complete`、`data-error` 同时表达当前、完成和失败。
- 自动运行到达 `awaiting_approval` 后必须暂停并聚焦审批人输入框。
- `prefers-reduced-motion: reduce` 下关闭旋转并将动效时长降至近零。

## 5. 响应式策略

| 宽度 | 结构 |
|---|---|
| `>= 1440px` | 工作台三栏：控制 / 主流程 / 证据审计。 |
| `1024–1439px` | 左侧控制 + 主流程；证据审计下沉为三列。 |
| `768–1023px` | 单列工作台，产品区和能力区改为单列。 |
| `< 768px` | 完整单列；隐藏次要导航；按钮满宽；状态机内部横向滚动。 |

所有 Grid 子项设置 `min-width: 0`，哈希使用断词规则；页面本身不得出现横向滚动。320px 下仍可创建事件、运行、审批与查看证据。

## 6. 可访问性

- 单一 `h1`；每个产品与工作台区块使用语义标题。
- 提供“跳至现场演示”链接。
- 原生 `button`、`select`、`input`、`textarea` 与 `dialog`，不使用 div 模拟控件。
- `:focus-visible` 使用高对比橙色轮廓。
- 事件队列、连接状态、运行状态与错误播报区域使用 `aria-live="polite"` 或 `role="status"`。
- 事件队列和时间线按钮同步 `aria-pressed`，状态机当前步骤同步 `aria-current="step"`。
- 对话框打开后焦点落到审批人；关闭后流程仍保留在正确状态。
- 长哈希可换行并保持完整文本，便于复制和辅助技术读取。

## 7. 性能与部署

- 原生 HTML/CSS/JavaScript，无构建步骤、外部字体、图片和运行依赖。
- 营销插画由 CSS 绘制；持续循环动画仅使用 `transform`/`opacity`。
- Python 服务环境使用真实 REST API。
- GitHub Pages、`file://` 或 `?demo=1` 环境由 `demo-api.js` 提供浏览器内存 API，状态保存到 `localStorage`；每次审计会按稳定序列化规则重新计算 SHA-256，而不是只检查哈希格式。
- Pages 工作流直接部署 `web/`，资源使用仓库相对路径。

## 8. 必须保留的工程契约

- DOM：`incident-board`、`scenario-select`、`approval-dialog`、时间线、审计、指标及所有现有业务 ID。
- 动作：`create-incident`、`refresh`、`advance`、`run-demo`、`reject`。
- API：场景、Agent、Skill、事件、指标、推进、批准和驳回路径保持不变。
- 安全：`app.js` 只使用 `textContent`/DOM 节点创建，不使用 `innerHTML` 或 `eval`。

## 9. 验收标准

- 成功样本：审批后进入 `resolved`，共 8 个事件。
- 失败样本：审批后验证失败并进入 `rolled_back`，共 9 个事件。
- 驳回样本：在写操作前进入 `rejected`，共 6 个事件。
- 审批门前不得产生执行或验证事件。
- 后端模式与 GitHub Pages 静态模式行为一致。
- 320px、430px、768px、1024px 和桌面断点无页面级横向滚动。
- 键盘可完成选场景、创建、推进、批准、驳回与证据选择。
